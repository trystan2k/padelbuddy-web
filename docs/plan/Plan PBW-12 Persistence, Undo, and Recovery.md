## Task Analysis

- Main objective: Deliver `PBW-12` as a client-only current-match persistence and recovery layer that stores the live session in IndexedDB using the existing ordered action-history model from `src/core/match`, restores recoverable active sessions on startup, supports replay-based undo for score actions only, and handles corrupted or incompatible persisted data exactly as specified in `docs/prd/prd-v2.md`, `docs/prd/scoring-spec.md`, `docs/prd/qa-spec.md`, and `docs/prd/release-incident-runbook.md`.
- Identified dependencies: `PBW-11` is done and already provides the critical pure-domain primitives (`projectMatch`, `undoLastScoringAction`, `continueMatch`, `deriveMatchState`) needed to avoid persisting derived state. The repository currently has no current-match app layer yet, but it already hints at the intended boundary through the empty `src/lib/current-match/` and `test/current-match/` directories, the client-only TanStack Start setup in `src/start.ts`, and the single home route in `src/routes/index.tsx`. The child issues should therefore extend those planned locations instead of introducing a second state architecture.
- System impact: Most work should land outside the pure scoring engine and concentrate in a thin application layer plus startup UX: `src/lib/current-match/**` for IndexedDB access, decoding, and session orchestration; `src/routes/index.tsx` and new `src/components/**` surfaces for resume/recovery/notice UI; `test/current-match/**` for browser-driven persistence coverage; and only small additive changes to `src/core/match/**` if a helper export is needed. The highest-risk boundaries are differentiating incompatible schema resets from truly corrupted data, preventing hydration/prompt flicker at startup, and making undo rely exclusively on replay rather than cached derived flags.

## Chosen Approach

- Proposed solution: Implement a small current-match session controller around the existing pure match domain. Persist a single canonical record in IndexedDB whose source of truth is the effective `MatchSetup` plus ordered `MatchAction[]` history, then derive `state` and `derived` on demand through `projectMatch`. Add a startup hydration state machine that resolves into one of four outcomes: empty session, recoverable session requiring resume/discard confirmation, incompatible-schema reset with a one-time notice, or corrupted-state recovery screen. Map the child issues directly onto this layer: `PBW-30` persistence repository, `PBW-31` schema gate/migration/reset handling, `PBW-32` undo integration through replay, `PBW-33` startup recovery UX, and `PBW-34` automated coverage.
- Justification for simplicity: This is the simplest effective approach because it reuses the deterministic replay model already established in `src/core/match/replay.ts`, avoids storing duplicate snapshots or derived state, avoids introducing Zustand/Redux or an IndexedDB wrapper dependency before there is evidence they are needed, and keeps persistence concerns isolated from scoring rules. Rejected alternatives: persisting full mutable match snapshots alongside the action log (more invalidation risk with no user benefit), and introducing a global app store plus complex migration framework before the first persisted schema exists.
- Components to be modified/created: add focused modules under `src/lib/current-match/` such as `indexed-db.ts`, `persistence.ts`, `schema.ts`, `session.ts`, and `bootstrap.ts` (exact filenames can stay flexible if a leaner split emerges); add or replace route-visible surfaces through `src/routes/index.tsx` and new UI components such as a resume dialog, recovery screen, and startup notice; extend `test/current-match/` with browser suites for IndexedDB-backed flows plus unit suites for pure schema/session helpers; update `ARCHITECTURE.md` only if the new current-match app layer becomes a stable project structure worth documenting.

## Implementation Steps

1. `PBW-30` - Establish the IndexedDB persistence core inside `src/lib/current-match/` using the browser-native API, with a single current-match store/object record that round-trips the canonical persisted session shape (`schemaVersion`, effective `setup`, ordered `actions`, and lightweight metadata such as save timestamp if needed). Keep write operations scoped to session save/load/clear helpers so React components never talk to IndexedDB directly. Pre-checkpoint: the persisted contract stores replayable inputs only, not derived state or full engine snapshots.
2. `PBW-31` - Add schema versioning and load-time decoding around that repository, returning explicit outcomes such as `ok`, `reset-required`, and `corrupt`. Treat incompatible versions as a silent reset path that clears persisted data and emits a one-time non-blocking startup notice for the current page load, while malformed current-version data is treated as corruption and preserved long enough to route the app into recovery mode. Risk/mitigation: if partial migrations start expanding beyond a simple decoder, roll back to a strict same-version reader plus reset-on-mismatch for this milestone instead of overbuilding a migration framework.
3. `PBW-32` - Introduce a small current-match session reducer/hook that owns the in-memory `setup + actions` pair, derives projection data via `projectMatch`, persists after successful mutations, and wires undo to `undoLastScoringAction(actions)` rather than manual state reversal. Any command path that changes official-match boundaries or endless-play eligibility should re-project from canonical inputs so serve, winner, active set, and `canContinuePlaying` always restore from replay. Risk/mitigation: if persisting endless-mode progress reveals the need to represent a continued match, persist the effective post-`continueMatch` setup as the canonical setup instead of inventing a second lifecycle history track.
4. `PBW-33` - Build the startup recovery UX as an explicit bootstrap state machine rendered from the home route or a dedicated current-match gate component. On mount, hydrate once from IndexedDB and branch as follows: no record -> continue normally; valid in-progress session -> show a resume/discard prompt with the resume action visually emphasized; corrupt record -> render a dedicated recovery screen with only `Reset and continue`; incompatible reset -> continue into the app and surface a one-time non-blocking notice after startup. Risk/mitigation: because `src/routes/index.tsx` still renders the foundation shell today, keep the integration surface shallow by introducing a route-level gate/wrapper instead of refactoring routing/navigation during this issue.
5. `PBW-34` - Add automated coverage in the same split already used by the repo: keep pure decoder/session logic in unit tests, and cover real IndexedDB + startup UX behavior in browser tests under `test/current-match/`. Prioritize scenarios for resume emphasized vs discard clearing, corrupted-state recovery, incompatible-version notice, replay-based undo restoring serve/winner/endless-mode eligibility, and persistence isolation between runs. Risk/mitigation: browser persistence tests can become flaky if state leaks between cases, so use a deterministic test database name strategy and explicit cleanup hooks before each scenario.
6. Finish the parent issue by running the full local quality gate from `AGENTS.md` (`pnpm complete-check`), updating lightweight architecture notes only if the new `src/lib/current-match/` layer becomes a stable convention, and verifying the child-issue sequence remains linear (`PBW-30` -> `PBW-31` -> `PBW-32` -> `PBW-33` -> `PBW-34`) so later work never depends on UI before the repository and hydration contract exist.

## Validation

- Success criteria: The app persists the current match in IndexedDB as ordered action history plus canonical setup, startup prompts to resume or discard any recoverable active session with resume emphasized, corrupted persisted data routes to a recovery screen whose only action is `Reset and continue`, incompatible schema loads may reset silently but always surface a one-time non-blocking notice after startup, undo removes only the latest score action while fully restoring derived state (including serve, winner/completion state, and endless-mode-related derived transitions), and `pnpm complete-check` passes.
- Checkpoints: Before Step 1, confirm the persistence source of truth is `setup + actions` and that no external state library or IndexedDB package is introduced unless native API friction proves material. After Step 1, repository tests or manual probes prove save/load/clear work against IndexedDB and that an empty database cleanly returns the no-session path. After Step 2, tests prove same-version records decode, incompatible versions clear and raise the startup notice, and malformed payloads route to the corrupt outcome; rollback note: if migration handling becomes ambiguous, ship reset-on-version-mismatch instead of partial migration logic. After Step 3, tests prove undo is equivalent to replaying without the last score action and that no persisted derived-state fields can drift out of sync. After Step 4, browser coverage proves hydration happens only once, resume is the emphasized startup action, discard clears the persisted session before entering normal flow, and the corrupt path exposes only `Reset and continue`. After Step 5, automated suites cover the acceptance criteria end to end, and after Step 6 both `pnpm test` and `pnpm complete-check` pass without introducing unrelated route or architecture churn.
