## Task Analysis

- Main objective: Deliver `PBW-10` by adding the repo's first full GitHub Actions delivery pipeline for pull-request checks, docs-only reduced CI, release automation through Release Please, preview deployment only for the Release Please release PR, production deployment only when a release is actually published, and CI artifact retention at 7 days. Assumptions: `PBW-8` and `PBW-9` remain complete and stable; GitHub-hosted runners and Cloudflare repo secrets are available; Conventional Commits remain the release source of truth; the release PR created by Release Please is the only PR that should receive a preview deployment. Approved CI constraint: workflows must not call `pnpm complete-check`; they must invoke `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, and `pnpm build` separately in that order when the full verification path applies, plus only already-defined repo checks when needed.
- Identified dependencies: The current repo already provides the local quality/build baseline in `package.json`, `vitest.config.ts`, `commitlint.config.js`, `README.md`, and `ARCHITECTURE.md`, but `.github/workflows/` does not exist yet. The build currently produces a static root `dist/index.html` plus a `dist/server` artifact, so deployment planning must explicitly target only the static Pages output. Likely files to add or update are `.github/workflows/*.yml`, release automation config files, `CHANGELOG.md`, and contributor/deployment docs.
- System impact: This issue establishes the repository's automation contract for branch protection, release gating, deployment timing, and artifact retention. Primary risks are (1) docs-only path filters accidentally skipping required code checks when non-doc files change, (2) release-PR preview or production deployment pointing at the wrong build output and publishing SSR artifacts, (3) deployment failures obscuring earlier lint/test failures, and (4) release automation drifting from `package.json` versioning and PRD release conventions.

## Chosen Approach

- Proposed solution: Use four focused workflows plus one shared path-filter pattern instead of a monolithic pipeline: `ci.yml` for PR/main verification and docs-only routing, `release.yml` for Release Please semantic versioning and changelog automation, `preview-release-pr.yml` for one Cloudflare Pages preview tied only to the Release Please release PR, and `deploy-production.yml` for production deployment only after a real release is created. Keep the verification path explicit in CI by calling `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, and `pnpm build` as separate sequential workflow steps rather than using `pnpm complete-check`.
- Justification for simplicity: This is the simplest effective approach because it reuses the repo's current single-package structure, preserves Release Please as the single release orchestrator, and narrows deployment automation to release-time events instead of every PR or every `main` push. Rejected approaches: (1) preview environments for every PR, which add deploy noise and cost without the new approval requirement; (2) production deployment on every `main` push, which no longer matches the approved release-gated rollout model; (3) heavier release stacks such as Changesets or semantic-release, which add more repository coupling than needed for one package compared with Release Please.
- Components to be modified/created: `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `.github/workflows/preview-release-pr.yml`, `.github/workflows/deploy-production.yml`, release config such as `release-please-config.json` and `release-please-manifest.json`, generated `CHANGELOG.md`, and documentation updates in `README.md`, `ARCHITECTURE.md`, and the release/deployment docs. Update `package.json` only if the named scripts need to be made CI-safe while preserving the required workflow command sequence.

## Implementation Steps

1. Reconcile the current local tooling surface with the explicit CI and release-gating constraints before writing workflows: confirm the full verification path will run `pnpm typecheck`, then `pnpm lint`, then `pnpm format:check`, then `pnpm test`, then `pnpm build`, and identify whether any already-defined repo checks must also run. Verify the exact static Cloudflare Pages upload directory from the existing build output so deployment targets `dist/` rather than any SSR artifact, and confirm how Release Please identifies its generated release PR so preview deployment can key off that PR reliably. Risk/mitigation: if any script semantics drift from CI-safe behavior, normalize the scripts before workflow wiring so release and deploy jobs consume the same deterministic commands.
2. Create `.github/workflows/ci.yml` as the authoritative verification workflow for pull requests and `main` pushes: add workflow/job concurrency to cancel superseded runs on new commits, run an initial path-classification job, and use a full-verification job whose steps execute the required commands in the exact order `pnpm typecheck` -> `pnpm lint` -> `pnpm format:check` -> `pnpm test` -> `pnpm build`. Upload relevant test/build artifacts with `retention-days: 7`, and keep failure visibility clear so later steps never hide earlier quality failures. During-implementation correctness check: a mixed PR that changes both docs and app/config files must route to the full check path.
3. Implement the docs-only reduced-check path inside CI using explicit path filters for `docs/**`, root `*.md`, and only the docs-oriented subset of `.github/**` files, while treating workflow/config files under `.github/` as code changes that force full checks. Keep the reduced path intentionally small: path validation plus lightweight markdown/workflow sanity checks are enough, but the full ordered verification sequence must be skipped only when no app or config files are touched. Rollback note: if added docs tooling proves noisy, fall back to deterministic path filtering plus minimal syntax validation rather than expanding into a separate docs toolchain.
4. Create `.github/workflows/release.yml` and supporting release config using Release Please: configure single-package semantic versioning from `package.json`, generate and maintain `CHANGELOG.md`, open/update the release PR from Conventional Commits, and emit a reliable signal when the release PR is created, synchronized, or merged and when the actual GitHub release is published. During-implementation correctness check: sample `feat` and `fix` commit histories should produce the expected minor/patch bump behavior and changelog sections without manual version edits.
5. Create `.github/workflows/preview-release-pr.yml` for preview deployment of the Release Please PR only: trigger when the release PR is created or updated, verify the PR matches the Release Please release PR identity, rebuild on the GitHub runner with the repo-defined CI-safe steps but never with `pnpm complete-check`, deploy the verified static output to Cloudflare Pages using a stable preview alias for that release PR, and expose the preview URL in workflow output or PR status/comment. Checkpoint: normal feature PRs must never trigger preview deploys, while updates to the release PR must refresh the same preview environment.
6. Create `.github/workflows/deploy-production.yml` for release-gated production deployment: trigger only after the release is actually created/published by Release Please, rebuild from the released commit with the explicit repo scripts needed for deploy packaging, deploy only the static Pages payload to the production environment, and document the exact GitHub secrets/environment variables required for Cloudflare authentication and project selection. Mitigation: prefer a release-event trigger over plain `push` to `main` so production deploys remain tied to actual releases instead of every merged change.
7. Reconcile repository documentation and branch-protection expectations with the final automation surface: update `README.md`, `ARCHITECTURE.md`, and deployment/release docs so they list workflow names, the explicit CI command order, docs-only behavior, the release-PR-only preview rule, the release-gated production rule, Cloudflare secret names, artifact retention, and the Release Please flow; then branch-test the workflows with one normal code PR, one docs-only PR, and one simulated release PR/update to verify triggers, outputs, required-check names, and PR/Linear linkage expectations remain aligned.

## Validation

- Success criteria: `PBW-10` is complete when pull requests run stable required checks with cancellation of superseded runs, docs-only PRs use the reduced CI path without ever bypassing full checks for mixed changes, the full CI path calls `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, and `pnpm build` separately in that order, only the Release Please release PR gets a Cloudflare Pages preview deployment, production deployment runs only when a real release is created/published, semantic versioning and changelog generation are automated through Release Please, and CI artifacts retain for 7 days.
- Checkpoints: Pre-implementation assumption check - verify the current scripts support the required CI sequence, confirm the exact static deploy directory from `pnpm build`, and confirm a reliable matcher for the Release Please release PR. Step 2 checkpoint - `ci.yml` exposes path detection plus the ordered verification steps, a force-push/new commit cancels the older in-progress run, and no workflow path uses `pnpm complete-check`. Step 3 checkpoint - a docs-only PR runs only reduced checks, while a PR that combines docs plus any app/config change still runs the full `typecheck` -> `lint` -> `format:check` -> `test` -> `build` sequence. Step 4 checkpoint - release automation dry-run or release PR simulation shows the expected next version, changelog entries, and release PR metadata. Step 5 checkpoint - only the Release Please PR triggers preview deployment, the preview URL stays stable for release-PR updates, and feature PRs never deploy previews. Step 6 checkpoint - production deployment runs only from the release-created/published event and never from ordinary PR branches or every `main` push. Step 7 checkpoint - contributor docs and release/deploy docs match the implemented workflow names, command order, release triggers, secrets, branch filters, and retention settings. Rollback guidance - if preview deploy, production deploy, or release automation destabilizes the pipeline, disable only the affected workflow and restore the last green CI-only checkpoint instead of rolling back the entire automation surface.
