## Task Analysis

- Main objective: Deliver `PBW-11` as a pure, deterministic match domain that projects canonical match state plus derived metadata from validated setup data and an ordered list of scoring actions, while staying aligned with `docs/prd/scoring-spec.md`, `docs/prd/prd-v2.md`, and the current `src/core/match` / `test/core/match` structure.
- Identified dependencies: `PBW-8` and `PBW-9` are already complete and provide the baseline module/export/test patterns; the existing domain surface is still minimal (`src/core/match/types.ts`, `src/core/match/index.ts`, `test/core/match/match.test.ts`), so `PBW-24` through `PBW-29` should expand that folder instead of creating a parallel architecture. Working assumptions to confirm before coding: the core engine accepts point-scoring actions and uses replay/truncation for undo, service remains team-based only, and endless play in this issue means exposing eligibility/transition boundaries rather than building the UI flow.
- System impact: This work primarily affects `src/core/match/**`, `test/core/match/**`, and likely `ARCHITECTURE.md` if the public module surface expands materially. The highest-risk areas are the deciding-set/best-of-1 rule combinations, continuous serve rotation across set boundaries, and keeping side-switch prompts and endless-play eligibility derived rather than hand-maintained mutable flags.

## Chosen Approach

- Proposed solution: Implement a small functional domain surface built around three layers: validated setup/types, a pure replayable scoring reducer for point actions, and derived-state helpers for serve indicators / winner / side-switch / endless-play metadata. Map the child issues directly onto those layers: `PBW-24` setup contract, `PBW-25` normal scoring transitions, `PBW-26` tiebreak variants, `PBW-27` serve rotation + derived state, `PBW-28` replay/determinism/undo boundaries, `PBW-29` regression coverage and quality verification.
- Justification for simplicity: This is the simplest effective approach because it keeps the engine data-first and test-first, avoids classes/state machines/event-sourcing frameworks, and lets undo be implemented by replaying a shorter action list instead of introducing reversible mutation logic. Rejected alternatives: a single monolithic reducer file with mixed validation/derivation logic (too hard to reason about), and an object-oriented match engine with mutable commands/history objects (more abstraction than the current repo needs).
- Components to be modified/created: expand `src/core/match/types.ts`; update `src/core/match/index.ts`; add focused modules such as `src/core/match/validation.ts`, `src/core/match/engine.ts`, `src/core/match/derived-state.ts`, and `src/core/match/replay.ts` (exact filenames can stay flexible if a simpler split emerges while coding); replace the current smoke test with targeted suites under `test/core/match/` such as `setup-validation.test.ts`, `scoring-core.test.ts`, `tiebreak-rules.test.ts`, `serve-derived-state.test.ts`, and `replay-determinism.test.ts`.

## Implementation Steps

1. Expand the domain contract for `PBW-24` by defining the canonical setup/action/state/derived-state types in `src/core/match`, then add setup validation that covers all v1 config combinations from the scoring spec, including best-of-1 conditional deciding behavior and side-switch prompt configuration. Pre-checkpoint: the types support all accepted setup options without yet encoding scoring logic.
2. Implement the normal scoring reducer for `PBW-25` as pure functions that consume the current canonical state plus a point action and produce the next canonical state for non-tiebreak play, covering advantage and golden-point behavior, game wins, set wins, and match completion boundaries. Checkpoint: deterministic unit tests prove the same setup + same point sequence always yields the same normal-play state.
3. Extend the reducer for `PBW-26` with standard tiebreak and deciding-set super tiebreak branches, keeping the deciding-set selection logic data-driven from the setup instead of special-casing formats throughout the reducer. Risk/mitigation: this is the easiest place to introduce branching bugs, so land explicit fixture-style tests for `Best of 3`, `Best of 5`, and `Best of 1` before refactoring for reuse.
4. Add `PBW-27` derived-state helpers that compute serving team, tiebreak serving progression, next-set first server continuity, winner metadata, side-switch prompt state, and endless-play eligibility strictly from canonical state plus setup, with no duplicate mutable bookkeeping. Checkpoint: serve rotation and prompt rules are validated independently from point progression tests so failures stay localized.
5. Add `PBW-28` replay utilities and invariants: project full match state from setup + ordered point actions, define undo as replay over the action list with the last score action removed, and cover determinism with replay-based tests that compare repeated projections and truncated histories. Risk/mitigation: if canonical state starts storing unnecessary historical snapshots, roll back to a slimmer replay model before expanding tests.
6. Finish `PBW-29` by converting the current smoke coverage into scenario-driven regression suites, updating exports/docs only where needed, and running the repo quality gate (`pnpm run complete-check`) once the domain tests are green. Final checkpoint: the domain module is documented by tests dense enough to protect all acceptance-criteria rule combinations, not just happy paths.

## Validation

- Success criteria: `src/core/match` exposes a validated setup contract and a pure replay API that correctly handles normal games, advantage/golden-point rules, tiebreak and super-tiebreak transitions, team-based serve rotation across sets, match winner and endless-play eligibility derivation, side-switch prompt derivation, and deterministic replay behavior for identical action sequences.
- Checkpoints: Before coding, confirm the engine boundary is `setup + ordered score actions -> state` and that side-switch prompts / endless play remain derived concerns. After Step 1, tests prove setup validation accepts every v1 option combination and rejects invalid best-of-1 / deciding-set combinations. After Step 2, normal-play tests cover deuce, advantage, golden point, game rollover, set rollover, and match completion stop conditions. After Step 3, tiebreak fixtures cover `6-6` entry, first-to-7 win-by-2, first-to-10 win-by-2, and deciding-set detection for best-of-1/3/5. After Step 4, derived-state tests confirm serving indicator continuity, tiebreak serve math, odd-game side-switch prompts, tiebreak every-6-points prompts, winner metadata, and endless-play eligibility. After Step 5, replay tests prove identical sequences are deterministic and truncating the latest score action fully restores derived state; rollback note: if undo requires non-score actions to pass, pause and re-confirm the domain boundary before adding more action types. After Step 6, `pnpm test` and `pnpm run complete-check` pass with the new domain suites included.
